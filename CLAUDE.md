# OdekoDashboards

Static dashboards built from Google Sheets data. Each dashboard is a folder
under `dashboards/`, built and deployed to GitHub Pages by a single GitHub
Actions workflow. `data.json` files are generated at deploy time and are
**never committed**.

## Layout

```
.mcp.json                              # registers google-sheets MCP
.claude/settings.json                  # permissions + SessionStart venv bootstrap
.claude/skills/new-dashboard/          # scaffolding procedure for new dashboards
tools/google-sheets-mcp/               # MCP server (Python, service-account auth)
.github/workflows/deploy.yml           # ONE workflow: build all data.json + deploy Pages
worker/<name>/                         # Cloudflare workers (deployed via wrangler)
dashboards/index.html                  # hub page listing all dashboards
dashboards/_shared/
  odeko-logo.png                       # shared logo, referenced as ../_shared/odeko-logo.png
  odeko.css                            # shared palette + page chrome (link before page <style>)
  odeko-charts.js                      # shared Chart.js defaults (include after Chart.js CDN)
dashboards/_lib/
  sheets.py                            # shared Sheets helpers for build scripts
dashboards/<name>/
  index.html                           # Chart.js + vanilla JS, single file
  scripts/build_data.py                # pulls sheet, aggregates, writes data.json
  data.json                            # generated by deploy workflow — gitignored
```

## Deploy pipeline

`.github/workflows/deploy.yml` is the only workflow. On an hourly cron
(plus extra weekday-morning runs for DCA1 Tracking), pushes to `main`
touching `dashboards/**`, and manual dispatch, it:

1. Runs every `dashboards/*/scripts/build_data.py` (discovered by glob),
   writing each dashboard's `data.json`.
2. Uploads `dashboards/` as the Pages artifact and deploys.

If any build script fails, the whole deploy aborts and the previous good
deployment stays live. Nothing is ever committed by CI, so `main` history
contains only real changes and branch protection is safe to enable.

A new dashboard needs **no workflow changes** — dropping a
`scripts/build_data.py` into its folder is enough.

## Adding a new dashboard

Use the `/new-dashboard` skill — it walks through intake (source file,
purpose, metrics, filters, cadence, slug confirmation) and scaffolding.
In short:

1. Inspect the source sheet with the `google-sheets` MCP
   (`get_spreadsheet_info`, `read_range` on `A1:Z6`).
2. Create `dashboards/<name>/scripts/build_data.py`:
   - CLI contract: `python3 build_data.py <output.json>` (default `data.json`)
   - Import the shared lib:
     ```python
     sys.path.insert(0, str(Path(__file__).resolve().parents[2]))
     from _lib.sheets import parse_num, read_range, sheets_service
     ```
     (`fetch_table`, `list_tabs`, and `csv_export` are also available.)
   - Parameterize `SPREADSHEET_ID`, `SHEET_RANGE`, filter values at the top
3. Create `dashboards/<name>/index.html` (copy DCA1's, adjust
   charts/columns). Link `../_shared/odeko.css` and, if the page has charts,
   `../_shared/odeko-charts.js`.
4. Add the dashboard to the hub list in `dashboards/index.html`.
5. Confirm the source sheet is shared with
   `sheets-mcp-bot@sheets-mcp-497414.iam.gserviceaccount.com`.
6. Commit + push to main. The push triggers the deploy workflow, which
   builds `data.json` and publishes the site.

## Viewing dashboards locally

`data.json` is not in git, so build it first (requires
`GOOGLE_SERVICE_ACCOUNT_JSON` in the environment):

```
python3 dashboards/<name>/scripts/build_data.py dashboards/<name>/data.json
```

Browsers block `fetch()` on `file://` URLs, so use a local HTTP server.
Serve from the `dashboards/` root so shared assets resolve:

```
cd dashboards && python3 -m http.server 8765
```

Then open http://localhost:8765/<name>/.

## Visual style (Odeko brand)

All dashboards must visually match `dashboards/dca1-onhand-eta/index.html`.
Use that file as the design reference for new dashboards.

Shared assets carry the design system — don't copy palette or header CSS
into pages:

- `dashboards/_shared/odeko.css` — `:root` palette variables, base
  typography, sticky header (`.brand` / `.logo` / `h1` / `.sub`). Link it
  before the page's own `<style>`; page CSS may override.
- `dashboards/_shared/odeko-charts.js` — Chart.js defaults (muted text,
  warm hairlines, Inter). Include after the Chart.js CDN script.

**Palette (CSS variables from `odeko.css`):**
- `--bg: #FBF7EC` — warm cream background
- `--panel: #FFFFFF` — card surface
- `--line: #E6DFCC` — warm hairline borders
- `--ink: #2A1408` — body text, deep coffee
- `--ink-2: #40180B` — headings, Odeko brand brown
- `--muted: #8A7B6A` — warm gray
- `--accent-yellow: #FFD100` — sparing accent (KPI left border, primary button)
- Status: `--green: #1F7A33`, `--amber: #B5660A`, `--red: #B42318`

**Conventions:**
- Font: Inter (with system fallbacks)
- Sticky header at top with `../_shared/odeko-logo.png` and h1 title
- KPI cards in responsive grid; values use `font-variant-numeric: tabular-nums`
- Section cards: white panel, 1px `--line` border, 8px radius, uppercase letter-spaced h3 header
- Status colors in charts use the palette red / amber / green
